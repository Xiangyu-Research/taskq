# How taskq works

The overview, install, command table, tests and exit codes are in [`../README.md`](../README.md). This file covers config fields, how
each part runs, where files live, and how to add things.

## Structure

```
                         hub (role hub in machines.py)
  clock every 30 min ─→ taskq tick (monitor/health.py)
                        ├─ check every machine, push problems (monitor/plain.py, push.py), record them in the hub database (queue/db.py, events.py)
                        ├─ queue/advance.py   downstream steps: look at the store for finished work, add the next step to the hub queue
                        └─ queue/feed.py → queue/relay.py   send tasks, transfer data, top up workers, fetch, archive
                               │   refill.choose: pick an executor for each unclaimed task
                               │   relay_remote.op / store_op: run an operation of queue/site_ops.py on that machine
           hub queue (queue/taskq.py, under the hub's state dir)
                               │
        ┌──────────────────────┼─────────────────────────┐
   store (role store)      executor (pueue)              executor (Slurm)
   data dir = home of results  root R: code/ queue/      root R: same
   site_ops: probe, export,    blobs/ data/ state/       sites/slurm.py submits worker jobs
   pull, collect, archive      worker (consume.py)       a worker (consume.py) runs in the job
        │                      resident in a pueue group       │
        └── data moves directly between the store and executors (sync/tunnel.py, or a local copy on the same machine), never through the hub's disk ──┘
   backup machine (role backup): results to archive are backed up from the store (queue/archive_task.sh)
```

- The hub claims tasks from the hub queue on behalf of each executor (the queue records which executor got it), sends the inputs there
  and puts the task in that executor's own queue (`R/queue`, same key as the hub queue); the worker there claims, trains and releases;
  when the hub sees it finished, it fetches the results to the store. Executors do not talk to each other.
- One machine can hold several roles; the one with `ssh=None` is the hub's machine and can also be an executor (commands run locally,
  transfers copy locally). An executor that sees the store's files keeps its data dir (`R/data`) apart from the store's data dir: neither
  may be the other or inside it (`taskq check`), or finished results there would count as already on the store and the executor's copy,
  the only one, would be deleted.
- Executors run bundles built by the hub (`queue/relay_bundle.py`: the core files executors need go into `scripts/taskq/` inside the
  bundle, plus the project's config dir and the dirs listed in `OUTPUTS["bundle"]`, minus `bundle_skip`, both read from `policy.py` at
  the commit being bundled); the bundle name is a content hash; it is pushed to
  `R/code/<bundle>` and `R/code/current` points at the one in use.

## Switches and config

The config dir holds two files: `machines.py` (machine table) and `policy.py` (how to use it). Fields, types and defaults are in
`queue/schema.py`; `taskq check` verifies against it (unknown fields are errors) and `taskq machines fields` prints it. The tables below
are generated by `taskq machines fields --markdown`, and `queue/test_readme.py` checks they match.

### Machine table

`MACHINES = {name: dict(...)}`, one entry per physical machine. Roles `roles`: `hub` (hub queue, health check), `store` (home of
results), `backup` (archive). An entry with `root` and `scheduler` is an executor; `scheduler` names its executor type (built in: pueue,
slurm; more from a project's `executors.py` plugin, see "Executor types"):

- `scheduler="pueue"`: write `workers=[dict(...), ...]`, one resident worker per entry (fields in the next table). The core names workers
  in order: with a GPU it is `gpu<number>`, without it `cpu` (`cpu<number>` when several); the id is `<machine>-<name>` and the pueue group
  has the same name.
- `scheduler="slurm"`: write `jobs=dict(gpu=..., cpu=...)` (sbatch options); how many, QOS and time limits are in `policy.py`'s `SLURM`.
  An entry's `slots` (default 1) is how many trainings one job runs at once (not an sbatch option: the worker reads the entry from the
  machine table when the job starts, so a change applies to jobs already queued); each
  task then gets its share of the job's cores and memory.

Pueue executors, the hub and the store all have the core's own pueue group `taskq` (`proto.IO_GROUP`: transfer, fetch, archive, env build,
unbounded concurrency). Manual groups are written in `manual_groups`; the core never queues into them (`taskq pueue-add` does). A `~` in
local paths such as `conda`, `root`, `data`, `repo` is expanded on this machine; a leading `~` in a remote command is left for the other
side to expand.

### policy.py

<!-- fields:POLICY_FIELDS -->
| field | type | default | description |
|---|---|---|---|
| `AUTO` | `auto` | required | which automatic parts are on: advance, envs, revive, smoke |
| `PAUSE` | `pause` | `{}` | {machine: (until 'YYYY-MM-DD HH:MM' or None, reason)}: while paused no connections or sends; resumes automatically |
| `HOLD` | `strs` | `()` | held steps (wildcard over step instance names, e.g. 'infer/*') |
| `PLACE` | `place` | `{}` | {step or training recipe: [executor, ...] \| 'any'}: allowed executors in preference order; absent = 'any' (any executor with such a worker) |
| `READY` | `intmap` | `{}` | {machine: how many unclaimed tasks to keep ready}; absent = 1 |
| `SLURM` | `slurm` | `{}` | {machine: dict(gpu={QOS: (time limit per part, jobs left for others)}, cpu=(QOS, time limit, max jobs))} |
| `OUTPUTS` | `outputs` | required | the project's outputs and entry points, see OUTPUT_FIELDS |
<!-- /fields -->

- `AUTO`: `advance` (queue the next step after training), `envs` (build envs automatically; may also be `{machine: [extra prebuilt envs...]}`),
  `revive` (restore pueued when it stops responding), `smoke` (smoke gate). A disabled part only records "what it would do" and changes nothing.
- `PAUSE`: paused machines are not contacted and get no tasks; they resume automatically at the deadline (hub local time), `None` means
  paused until the entry is removed. When the backup machine is paused, results that need archiving are released directly.
- `HOLD`: matching step instances are not queued (`advance` skips them).
- `PLACE`: keys are step names or training recipe names; values are allowed executors (order is preference) or `'any'`. Intersected with
  the spec's `machines`.

Names usable in templates: recipe params, `each` values, `names`, and `{data}` (the data dir on the executor). `{name}` puts the value
in as is (in a command the shell splits it at spaces and reads any shell syntax in it); `{name:q}` puts it in shell-quoted, as one word
whatever it holds (use it for values that may hold spaces, quotes, `;`, `$` and the like). Instance ids: a per-task step
is `<step>/<experiment id>_<short>`, an experiment-level one is `<step>/<experiment id>`, and a `FINAL` one is `<step>`. `taskq exp steps`
lists expanded steps, `taskq dag` shows the order, and `taskq who <file>` tells whose output a file is.

### Recipes

A recipe (`command` in `queue/recipes.py`, plus `RECIPES` in the project's `recipes.py`) is a template for a kind of task: `params` are
parameters and defaults (`REQUIRED` = must be given, defaults may use `{other param}`), `open=True` lets a task carry params not listed
here; the other fields form the task spec (templates, `{param}` replaced by the value).
A task param named after a field in the table below (and not in the recipe's `params`) sets that spec field only where the recipe lets
tasks set it, otherwise the task is refused: on any recipe `key`, `machines`, `res`, `device`, `out_gb`, `owner` (`schema.TASK_SETS`);
the fields the recipe lists in `override` (such as `override=["vars", "inputs"]`); every field on an open recipe. The experiment
table's `fields` and a smoke definition's `vars` reach the spec the same way, so the recipe lists them in `override`. `cmd` and
`inputs_cmd` (code run on executors and the store, `schema.OPEN_ONLY`) cannot be listed: only an open recipe takes them from a task.
On a closed recipe a value a task gives that `cmd` or `inputs_cmd` puts in as is (`{name}`, directly or through another param's
default) may hold only letters, digits, spaces and `_@%+=:,./-`, so it cannot add shell syntax to the command; the recipe writes
`{name:q}` where any value should pass as one word.

### Plugins

Plugins are found by filename in the plugins dir (`.taskq.toml`'s `plugins`); only these names are read per kind, and they import only
`taskq_api` (`queue/taskq_api.py`):

| file | exports | purpose |
|---|---|---|
| `recipes.py` | `RECIPES`, `HOOKS` | recipes; hook `model_of` (result dir -> the model param of the task that trained it) |
| `relay_plugins.py` | `PLUGINS`, `ACCEPTS`, `VIEW_ROOTS` | how to list inputs, build views and check results when sending to an executor (`queue/relay_plugins.py`, `sites/names.py`) |
| `consumers.py` | `CONSUMERS` | consumer plugins (see "Consumers") |
| `smoke.py` | `SMOKE` | smoke definitions (see "Smoke") |
| `labels.py` | `STEPS`, `QUIET`, `PLAN_TITLES` | plain words for pushes and progress reports (`monitor/plain.py`) |
| `executors.py` | `EXECUTORS` | more executor types `{scheduler value: module}` (see "Executor types") |
| `readers/*.py` | `PROGRESS`, `INFO`, `TRAINED` | how to read progress, training settings and whether a round finished (`queue/spec.py` reads them, standard library only) |

Merging tables with duplicate keys is an error.

A task without its own progress reader (a plain command) can still report progress: `run_task.sh` gives its command
`TASKQ_PROGRESS` (`<out>/PROGRESS.json`). A command that writes `{"done": n, "total": m}` there (a temp file, then rename) gets a
percentage, and from the points each health check sees (kept under the data dir in `logs/progress.json` for 6 h) an expected
finish time, in `taskq status --all` and `taskq progress`, carried to the hub like training progress. A task with its own reader
ignores the file.

## Where to look when something is wrong

| want to know | look at |
|---|---|
| what is wrong now | `taskq problems` (the "Needs you" list of `taskq status`, each item with its id for `taskq notice ack`, then due notices; `--all` also lists info problems and ones not yet due for a push) |
| what happened | `taskq events` (`--key`, `--site` with a machine name or label, `--source`, `-f`; relay lines carry their machine in `site`); `relay`, `feed`, `advance` and `health` also write a plain text log (`OUTPUTS`'s `logs` dir, default `logs/` in the state dir: `relay.log` etc.; each machine's `on_boot.log` and GPU usage records are in its own state dir: its root's `state/` when it has one) |
| one task | `taskq show <key>` (spec, state, failure and skip records, the end of the last failed run's log), `taskq log <key>` (each part, events, hub task records), `taskq progress --key <key>` (each change of hub queue state, progress, machine or word) |
| what a state word means | `queue/taskstate.py` holds the one rule (words in `proto.TASK_WORDS`): `taskq status`, `taskq status --all --json` (`word`, `where`) and the progress snapshot each health round all use it |
| what this round would do | `taskq plan` (read-only: the problems, downstream steps and sending of one health check) |
| a machine's agent | `taskq site agent status` (when each agent last called the hub); on that machine `~/.local/state/taskq/agent-<machine>.log` |
| one executor | `taskq site status <machine>` (name or label; `bundle`, `resend`, `env`, `envs` and `taskq smoke` too, `site setup` takes the name only; its queue, in the format of `taskq status --queue`), `taskq site envs <machine>` (envs); what relay last read there is a `site` row in the hub database |
| the worker itself | `data/logs/workers/` under the executor root (worker, GPU pad, Slurm job output); `pueue log` on a pueue executor |
| training output | part log `data/logs/tasks/<key>__<job>_part<part>.log` (on the executor; the fetch brings it to the same place in the store) |
| whether config is right | `taskq check` (`--quick` does not contact the store) |

Problem ids are `<kind>:<machine or key>...` (kinds in `proto.ALERTS`); each problem is kept and listed on its own and disappears on its
own when fixed. Pushes go by cause (`proto.ALERT_RULES`: a cause template per kind, and kinds never pushed): problems with the same
cause are one line in one push per round ("+N more with the same cause"), pushed again only when their number doubles or their level
rises, and `taskq status` lists them as one item. `taskq problems --json` gives each problem's `cause`, `push` and `members`. pueue
tasks of transfer and env steps (`proto.RELAY_OWNED`) are reported by those steps, not again as `pueue:` problems. "Things that
happened" such as a reboot are acknowledged with `taskq notice ack`. A slow round (`health:slow`) names its three slowest parts (the
`tick_steps` meta row holds each part's seconds).

## How it runs

### Task queues

The hub queue and each executor queue are the same kind of queue (`queue/taskq.py`): `tasks.jsonl` has one task per line (nice `nice`,
arrival `order`, key, recipe, params), `claims/<key>/` is a claim (heartbeat every 5 minutes, stale after 20 minutes without one), and
there are records for failures, skips, missing inputs, releases and stops. Task states are in `proto.STATES`. The hub keeps the same
records in its database `taskq.db` instead of files (`queue/qstore.py`, tables `task`, `claim`, `mark`, `line`, `smoke`, `switch`), each
edit one transaction; executor queues stay files. The hub queue has no `ENABLED` file: its master switch is the `queue` row of `switch`.

A failure keeps the end of its own log: `release --failed` also writes `failtail/<key>`, the last 50 lines of the run's part log (each
cut to 300 characters, about 8 KB at most; for progress bars only the text after the last carriage return), and the hub's check copies
it into the hub queue (with the machine), so it stays after the executor drops the task and its logs. `taskq show <key>` prints it with
the failure and skip records; `taskq status --queue` and `taskq site status` add its last meaningful line (`; last failure: ...`) to
the task's line, and the hub's release, event and alert for the failure name it too.

Commands that edit the hub queue (`add`, `set`, `nice`, `take`, `rm`, `stop`, `resume`, `unskip`, `proto.HUB_EDITS`) or write the hub
database (`note`, `notify`, `notice set` / `clear` / `ack`) refuse to run inside a task's command when what they would write is the
executor's own copy (`TASKQ_TASK` set by `run_task.sh` and `TASKQ_ROOT` pointing at that executor root; `cfg.refuse_in_task`): there
`taskq add` would silently go to the executor's queue, where the hub never placed it, and `taskq note` to a database nobody reads. Run them
on the hub without `TASKQ_ROOT` and `TASKQ_STATE`. The hub's own calls to executor queues (relay, `taskq nice`) run outside task
commands, and a local executor's calls drop `TASKQ_TASK` with the other hub-only variables.

Claim order: lower nice first; within a nice, half-done tasks first (has a checkpoint, or this machine has part logs and no failure record);
then arrival order. The whole queue pauses claiming after 3 failures in 3 hours. A `taskq stop`ped task is not claimed again; a worker
of the same queue running it stops and releases it within 30 seconds, while for a task the hub sent to an executor the stop reaches
the executor at the hub's next check (every 30 minutes); `taskq resume` undoes it. After the release the entry stays in the
executor's queue as `stopped` (its results kept) and does not disappear: check that a stop has finished by the "released" line in
`taskq events --source relay` or by the hub queue's state. Resumed before the release, the task continues on the same executor;
resumed after it, the next check deletes the executor's copy and its results and the hub queue dispatches it again with its current
params (a way to resend a not-yet-started task with changed params).

### Workers (consume.py) and consumers

A worker is `queue/consume.py` (`queue/worker_start.sh` activates the worker env, the second item of the machine table's `conda`,
and starts it; a name in `envs` is activated the same way as for tasks): it claims tasks from this
machine's queue, starts `queue/run_task.sh`, collects exit codes, sends heartbeats, stops and releases. `run_task.sh` activates the env
from the spec, sets env vars and runs the command at the project root inside the bundle, writing output to the part log; the training
command must resume from its checkpoint (after a release another worker continues from it). A spec may hold tokens in `vars`, so it
never goes on a command line, which any user of the node can list: the worker starts `run_task.sh --stdin` with the task's arguments
on stdin (from a file only its account can read, already unlinked), `run_task.sh` hands them to `spec.py` on stdin, the store's
`archive_task.sh` and the bundle gate get the spec the same way, and the worker log records only the task name. Training never outlives its task: the
command runs in its own session, whatever it leaves there when it exits is stopped, and a watcher stops the training once the worker
that started `run_task.sh` is gone (killed) or `run_task.sh` itself was killed, so a killed worker never leaves training on the GPU
for a new worker to stack another task onto. Stops the worker sends itself (`taskq stop`, its own stop signal or hours window, stall
handling, a claim taken over) release the task without a failure; a task whose training or `run_task.sh` dies of a signal the worker
did not send (an out-of-memory killer, an admin) is released as a failure, so one killed every time reaches the failure limit.

#### Env vars of workers and tasks

A worker inherits these from its launcher, `run_task.sh` from the worker, and the task's command from `run_task.sh` (names in
`proto.RUN_ENV`, the `TASKQ_*` ones in `proto.ENV`):

| env var | set by | meaning |
|---|---|---|
| `WORKER_ID` | the pueue worker command (`sites/mtab.py` worker_env) | the worker's name, `<machine>-<worker>`; a Slurm worker takes its job id instead |
| `WORKER_DEVICE` | the pueue worker command; `queue/cpu_worker.sbatch` sets `cpu` | which tasks the worker claims: `gpu` (unset) or `cpu` |
| `CUDA_VISIBLE_DEVICES` | the pueue worker command | the worker's GPU (the machine table worker's `gpu`) |
| `TASK_GPU_IDLE` | the pueue worker command | minutes no one else may have used the GPU in the GPU usage records before a task starts (the worker's `idle`): the `gpu_idle` plugin checks it before claiming, `run_task.sh` started by hand waits for it |
| `TASK_WAIT_GPU` | `spec.py shell` in `run_task.sh` | most minutes `run_task.sh` waits for a busy GPU, from the task's `res.wait_gpu` (empty = wait forever); it replaces the worker's `wait` that the pueue worker command sets |
| `TASK_KEY` | the worker | the task's name |
| `TASK_JOBTAG` | the worker | the job name in the part log name and first line: the worker's name, plus `-<start time>` for a resident worker; set means started by a worker (one try, and the training stops once the worker is gone); unset: `<hostname>-<time>` |
| `TASK_PART` | the worker | the part number in the part log name (`1`; unset: `1`) |
| `TASK_CPUS` | the worker | cores for this task: the worker's cores divided by its slots |
| `TASKQ_ADMITTED` | the worker | `1`: the worker checked the GPU before claiming, `run_task.sh` does not wait for it again |
| `TASKQ_STAGE_ROOT` | the `slurm` consumer plugin | node-local staging root: with `res.local_inputs` the inputs are copied there |
| `TASK_INPUTS_ROOT` | `run_task.sh` | where the command reads its inputs, at the same relative paths as in the data dir: the data dir, or the node-local copy |
| `TASKQ_DATA`, `TASKQ_LIB` | `run_task.sh` | the data dir; the core's `queue/` (the core's `bin/` comes first on `PATH`) |
| `TASKQ_PROGRESS` | `run_task.sh` | where the task's command may write its progress: `<out>/PROGRESS.json` |
| `TASKQ_TASK` | `run_task.sh` | the task's key; with `TASKQ_ROOT` set, hub queue and database edits from the command are refused (see "Task queues") |
| the spec's `vars`, the machine table's `task_vars` | `run_task.sh` | exported for the command (minus `task_unset`; a `task_vars` entry set already keeps its value) |

`RUN_TASK_TRIES`, `RUN_TASK_POLL`, `RUN_TASK_GPU_POLL`, `RUN_TASK_STOP_WAIT`, `RUN_TASK_BOSS_POLL` and `WORKER_TEST_GPU` replace
timings and GPU records in tests only. The shell variables `spec.py shell` prints for `run_task.sh` (`TASK_CMD`, `TASK_OUT`, ...)
are in `proto.SHELL_VARS`.

#### Consumers

Differences between executor kinds live in consumer plugins: the core's `queue/consumers/` (in this order), then the project's
`consumers.py` `CONSUMERS`. A plugin is a module or dict; every hook (`consume.HOOKS`) is optional:

| hook | when |
|---|---|
| `active(w)` | start: whether this plugin applies (absent = yes) |
| `setup(w)` | start: set the worker's name, concurrency, time limit etc. |
| `admit(w)` | before claiming another task: returning a reason means do not claim yet |
| `before_start(w)` | before training starts |
| `env(w, env)` | before training starts: change env vars for `run_task.sh` |
| `tick(w)` | every round |
| `idle(w, why, now, since, err_since)` | nothing running: return seconds to sleep, `None` = exit |
| `on_exit(w)` | before exiting |

A hook that raises never stops the worker: it is logged with the plugin and hook names and the worker falls back (a failing `active`
keeps the plugin, so its `admit` still decides; a failing `admit` means do not claim now; a failing `before_start` starts anyway; a
failing `env` leaves the env vars unchanged; a failing `idle` checks again after `TASKQ_POLL` seconds and exits once idle for
`TASKQ_IDLE_MAX`). Any other unexpected error in the worker goes through the normal shutdown: it stops training, releases the claims
of what has stopped, runs `on_exit` and exits 1.

| plugin | what it does |
|---|---|
| `slurm` | in a Slurm job: job id as the worker name, concurrency from the jobs entry's `slots` (read when the job starts, default 1), job time limit, node-local staging dir, exit after an idle period |
| `resident` | resident worker in a pueue group: worker id as the name, cores and concurrency from the machine table's worker, exit after an idle period (exit 0, the hub starts it again next round) |
| `gpu_pad` | with a GPU pad: grow it to floor before training, subtract its memory when computing free GPU memory |
| `window` | the machine table worker's `hours`: do not claim outside the window; at the end of the window stop and release current tasks and exit |
| `gpu_idle` | claim only when, on every GPU in `CUDA_VISIBLE_DEVICES` (by index or UUID), no one else's processes are there and the usage records show no one else in the last `idle` minutes; a GPU nvidia-smi cannot tell about (missing, failing, timing out, unreadable output) is not free (`run_task.sh` waits the same way when started by hand) |
| `gpu_share` | a second task on one GPU: after the first has trained for a while, claim another when average utilisation is low and half the memory is still free |

How many tasks share a GPU and when to top up follow only this live state, never a model classification.

#### Executor types

A machine's `scheduler` names its executor type, a module registered in `sites/executors.py` (`TYPES`: built-in `pueue` ->
`sites/pueue.py`, `slurm` -> `sites/slurm.py`, plus the project's `executors.py` `EXECUTORS`; reusing a built-in name is an error). The core
reaches a type only through `executors.of(name)` / `executors.get(type)`; `taskq check` accepts only registered types and reports a plugin type
missing part of the interface. Each type provides (full signatures in the `sites/executors.py` docstring):

| name | used by | what |
|---|---|---|
| `RESIDENT` | `taskq check`, `taskq status` | workers are resident, one per `workers` entry (slots, hours windows); only such types may write `workers` |
| `check(name, m)` | `taskq check` | problems with the fields this type needs |
| `workers(name, m)`, `groups(name, ws)` | `mtab.workers`, `mtab.groups` | worker list; the pueue groups it runs on the machine |
| `status_args(name)`, `read_status(A)`, `parse_status(name, raw)` | `relay.remote_status`, `site_ops status` | extra status args; the raw read on the executor (inside the bundle); the hub's parse into the remote status (`jobs`, `squeue`) |
| `plan(name, rs, run)`, `describe(sub)`, `start(name, subs, run)` | `relay.topup`, `taskq plan`, `relay.submit` | which workers to start this round (built-ins: `refill.pueue_plan`, `refill.slurm_plan`) and their problems; start them |
| `bundles(cur, live)` | bundle gate | bundles in use a sent spec must run on |
| `env_launch(name, m, minutes)` | env builds (`sites/envs.py`) | how a build runs on a CPU there (None: nice, no GPUs, time limit) |
| `worker_cmd(name, w)` | `taskq machines show` | the command that starts a worker, or None |

`site_ops status` loads the type on the executor, so a project type's module must be in the bundle (plugins dirs inside the repo are).

#### Workers in Slurm jobs

The hub tops up Slurm executors each round through `refill.slurm_plan` (`sites/slurm.py` submits `queue/worker.sbatch` or
`queue/cpu_worker.sbatch`): when the machine has tasks needing a GPU (ready and unclaimed, or training), fill every QOS quota in
`SLURM[machine]["gpu"]` so queued jobs keep accumulating queue time; pure CPU tasks are submitted up to the limit in `SLURM[machine]["cpu"]`.
The job's argument is `R/code/current/.../worker_start.sh`; `current` is resolved when the job starts, so it uses the bundle of that
moment; a worker switches to a new `current` only when claiming a new task.
When inputs must be copied to node-local disk (`res.local_inputs`), the copy runs in the background after training starts
(`queue/inputs.py`). The node-local dir must be a private dir of this account (created 0700; one made by another account, or a link,
means inputs are read in place), only this account's other job dirs on the node are hard-linked from or cleaned up, and a local blob
is used only while its sha256 is known to match (its `.st` record, else checked again by the copy).

### Sending tasks: feed -> relay -> refill.choose

There is one entry point for sending tasks: the health check calls `run_all` in `queue/feed.py`, which hands off to `queue/relay.py`. Each round:

1. **Read** (`prepare`): one ssh per unpaused executor reads its queue, each task's progress, jobs, free space, envs and bundle
   (`site_ops status`, one `@@JSON` line); when its bundle differs from the hub's, push the new one first and read again. When space is
   below the first `budget` item, clean up (see "Data").
2. **Per-machine actions** (`plan`): for each task assigned to this machine in the hub queue --
   - not yet in its queue -> `stage` (queue `taskq internal stage` in the core group: the store sends missing data, builds the view, adds it
     to that queue; exit 75 = does not fit this round, transfer next time);
   - queued or training there -> `beat` (renew the hub queue claim); finished there -> `fetch` (fetch to the store and verify);
   - present on the store -> `drop` (remove the task and results there); if it needs archiving, `archive` first (store backs up to the
     backup machine; release only after success);
   - failed there: no progress -> `release --skip` (this machine will not claim it again); with progress -> keep the claim and report it;
     a failure tail there that the hub queue does not have yet -> `failtail` (copied into the hub queue for `taskq show`);
   - stopped in the hub queue, stop undone, nice changed -> `rstop`, `rresume`, `rnice`; missing inputs there -> `restage`;
     `taskq nice` on the hub does the `rnice` part at once for the keys it changes (`relay_remote.push_nice`: reads that queue, then
     `set-nice` there for keys queued or running there; a running task keeps running, only its stored nice changes; keys not sent yet,
     done, failed or bad are left as is; paused or ssh master down: not contacted, the round follows later); `-n` prints both sides only.
     `rnice` reads the hub queue's nice again just before sending (`relay.hub_nice`): a round can run for minutes, and a value
     `taskq nice` set meanwhile is not set back to the one the round read;
   - stopped in the hub queue before it reached that queue: the staging does not send it (it asks the hub queue before the transfer
     and again before placing and adding), and the claim is released only once its staging has ended;
   - blocked by the bundle gate or smoke gate -> `hold`; unblocked -> `unhold`.
   - in that queue but no longer assigned to this machine in the hub queue (released, assigned elsewhere, removed): running -> reported;
     finished -> `fetch` first, and `drop` only once the store has the results; otherwise stopped or dropped there;
   - a failed `stage` / `fetch` / `restage` (mostly not the task's fault: tunnel down, busy disk timing out) is queued again at the next
     check, reported only after `XFER_TRIES` (`relay.py`) failures within one claim since the bundle last changed (a new bundle gets
     fresh tries); stopped by hand is not retried; an old failed one queued again later is not reported by the health check. Blob work
     for one executor (`missing` -> `ingest` -> `push` -> `view`) runs one transfer at a time (a lock per executor on the hub), so
     stagings sharing files do not send the same blob twice.
3. **Assign** (`assign`, `refill.choose`): unclaimed tasks in the hub queue are assigned to machines in one pass. Order: nice -> half-done
   first -> arrival order. Each task's possible executors = intersection of `PLACE[step or recipe]` and the spec's `machines`, limited to
   machines with that worker kind (gpu / cpu); drop machines that skipped it (all skipped -> report `tqblocked`); a half-done task only goes
   to the machine with its progress; tasks whose inputs are already there come first. A machine must pass each of (`Site.fit`): has that
   worker kind, env ready, free slot (ready unclaimed below `READY[machine]`, negative nice does not count; when full it may swap out one
   without progress), inputs present on the store, fits (after inputs + `out_gb` at least the second `budget` item remains; with `blob_cap`
   the blobs disk is counted separately), plugin accepts, bundle gate and smoke gate do not block. Input sizes are measured on the store
   (`site_ops probe`).
4. **Do** (`finish`): carry it out, then top up workers: on a pueue machine start a worker when it is in its hours, none is alive, the
   previous one did not fail, and there is a ready unclaimed task of that kind there; on a Slurm machine submit jobs by the rules above.
   How many to start is computed only here; adapters in `sites/` only read state and follow instructions.

Alert when a machine is unreachable for more than 2 hours; send no tasks while all workers are outside their hours. Tasks assigned to a
name that is not an executor are reported by `feed.py`.

#### Bundle gate

Before sending a spec, run what the executor does with the spec on the hub using the bundle in use there (`queue/bundle_gate.py`); if it
fails, do not send (`hold`, report `bundlegate`) and check again after that machine switches bundles. When only an older bundle that
running workers still use cannot run it (they switch at their next claim), the report is recorded as info for `proto.HELD_PATIENCE`
before it is pushed.

### After training: advance and flow

`queue/flow/compile.py` derives instances and order from the experiment table: within one task in order (training -> `after`'s first step
-> second ...); an input (wildcards included) that falls in another instance's outputs is ordered after that instance, across experiments;
inputs that fall in no output are raw data. Checks: unknown names in templates (`cmd` and `inputs_cmd` are filled here too, so a bad name
shows at once), wildcard outputs, overlapping outputs, an input inside its own outputs, `temp` patterns that leave the output or match a
done marker, and cycles.

Errors stay local. Each experiment table loads on its own (`experiments.py`): a table that cannot be imported, an experiment or `FINAL`
step with bad fields, an experiment whose tasks do not resolve, a duplicate experiment id or task name leaves out just those entries, and
the rest load; a queued task whose experiment is not found while entries are left out does not resolve (status shows it as bad). An
error in a step blocks that instance and every instance after it (a step whose outputs cannot be filled keeps its readers waiting through
its outputs with the unknown names as wildcards); the others go on. `taskq check` lists every error, and advance reports them each round
(`advance:flow`).

`queue/advance.py` each round:

1. checks on the store whether each instance is done (all `done` files present; still being fetched does not count);
2. adds to the hub queue any instance whose prerequisites are done, which is not done itself, not blocked by an error, and is not in the
   queue (recipe `command`, key = instance id, `step` = step name); which machine it goes to is decided by `PLACE` when sending;
3. steps with `rerun=True`: when an input is newer than the done file, delete the done file on the store and queue it again;
4. `temp`: after every instance using it is done and its results are on the store, delete those temp files on the store and record it in
   events. The store deletes files and links only: a matching directory goes once it is empty (`dir/**` empties one), and one that still
   holds files is reported. While entries are left out of the experiment tables (or a step's inputs cannot be filled) no temp files are
   deleted: a step reading them may be among those entries.

`HOLD` matches are not queued; with `AUTO["advance"]` off it only writes "what it would queue".

### Store and site_ops

All operations that read or write data run on the machine holding the data: the hub runs `queue/site_ops.py <op>` inside that machine's
bundle through `relay_remote.op` (executor) or `store_op` (store) (arguments are JSON on stdin, the result one `@@JSON` line). The list of
operations is at the top of `site_ops.py`: for an executor root, `status`, `states`, `missing`, `pin`, `ingest`, `view`, `list`, `drop`,
`gc`, `env_mark`; for the store, `done`, `probe`, `rm`, `export`, `pull`, `collect`, `smoke`, `archive`; and `push` for sending files.

### Data: blobs, views, fetching

- **blob**: data files on an executor are stored by sha256 at `R/blobs/<first two>/<sha256>` (`proto.blob`); the adjacent `.st` records size
  and mtime once the sha256 is checked (when ingested, or by the receiving side of `push` in the same read that checks the MD5, after the
  file is in place), so later operations compare those instead of reading the file again; a mismatch means drop and ingest again. A blob
  without a record counts as missing for `missing` (no hashing under its short timeout); `ingest` then checks its sha256 and records it. A pushed
  file whose content is not its sha256 is not placed and not sent again in that run. The store's `export` lists the files and sha256 for a task (cached in
  `R/state/hashes.db`), and `push` sends only what is missing there; existing files on the same disk are hardlinked in (`ingest`).
- **views**: each task's inputs under `R/data` are built as symlinks to blobs following the store data dir's relative paths (`view`, never
  overwriting real files; a half-built dir contains `.incomplete`), and commands read paths under `{data}` as usual. A task being
  transferred or whose view is not ready pins its blobs (`R/state/pins/`).
- **cleanup** (`gc`, `queue/relay_store.py`): when free space is below the first `budget` item, delete views the hub queue no longer wants
  first, then blobs with no links by least recently used; pinned and half-transferred ones are left alone. `cap` and `blob_cap` limit the
  root and blobs. On the store, whose blobs are hard links of its data dir, a blob left with one link (its data-dir file was deleted or
  replaced) holds space for nothing: once every `ORPHAN_EVERY` the hub also has the store remove such blobs whose last change is at least
  `ORPHAN_KEEP` old (not used by a view, not pinned), whatever the free space. This sweep walks the store's whole data and blob dirs, so it
  runs at the end of the health check, after every executor has been sent its work, with its own timeout (`ORPHAN_GC_TIMEOUT`).
- **fetch** (`fetch` -> the store's `pull`): that side lists outputs (`list`, same rule as "done") and fetches them to `.relay_in/<key>` under
  the store data dir, verifies them, moves them into place, and writes marker files (`MANIFEST.json`, top-level files) last. Done is judged
  by actual files on disk; while a copy, fetch or transfer is running it is not done and the source is not cleaned up.
- **archive**: tasks with `archive=True` are backed up from the store to the backup machine and verified by `queue/archive_task.sh` after
  the fetch.

#### Transfer

Bulk files between the store and executors go through `sync/tunnel.py`: the store runs a file service at the machine table's store
`transfer` address (a temporary address with `quick`), and all connections are initiated by the executor. The machine table's `tunnel`
says which direction this machine uses: `push` (store -> here, the other side downloads; on Slurm it may run on the `transfer_job` node),
`pull` (here -> store, chunked upload). Transfers on the same machine (such as a store that is also an executor, or an executor with
`ssh=None`) copy directly, hardlinking blobs, write to `.tunnelpart` and rename. `taskq tunnel rsync` is an rsync stand-in: transfer
through the tunnel first, then run rsync unchanged.
The public address must be https (plain http only to localhost; `taskq check` reports it). Each transfer is a session whose random
token travels in a request header, never in the URL, and allows only the files in its list; received files never get setuid, setgid
or sticky bits. One file server process on the listen address serves all sessions and exits when idle; before using it, a transfer
checks that the server answers a challenge with a key only this account can read (`tunnel_srv/serve.key` in the state dir, 0700):
another account's process on that address makes the transfer fail without sending it anything, and our server of an older version
is stopped and replaced.

#### Agents

Every command the hub runs on another machine (reading status, adding tasks, starting workers, submitting Slurm jobs, starting and
polling transfers, archive backups) goes through `sync/xssh`, an ssh stand-in. For a machine with `agent=True` in the machine table
it goes to that machine's resident agent (`sync/agent.py`) instead of ssh; for every other machine it runs the real ssh unchanged.
The agent only connects out, to the same file server and public address as transfers (a VPN or inbound ssh is not needed once it
runs): it long-polls `/agent/<machine>/next` for commands, runs each in bash in the home dir as an ssh login would (`~/.bashrc`
first, a clean environment however the agent was started), streams stdin in and stdout / stderr back while the command runs (so
`rsync -e xssh` works), and reports the exit code. A caller that is killed stops refreshing its `.alive` file and the agent stops
the command. An agent not seen for 2 minutes is unreachable: xssh exits 255 at once, as ssh does when it cannot connect, and
`-O check` answers for an ssh master the same way.

- Mailbox on the hub: `tunnel_srv/agent/<machine>/` in the state dir (`key`, `seen`, `info.json`, `inbox/`, `run/`; details in
  `sync/agent_box.py`). The file server stays up while any machine has a mailbox; each health round restarts it if it died.
- Security: each machine has its own key (on the hub in the mailbox, on the machine in `~/.config/taskq/agent-<machine>.json`,
  both 0600). Every agent request is signed (timestamp within 5 minutes, nonce never reused); commands, stdin and agent code from
  the hub carry the hub's signature, and the agent refuses anything without it, so the public address and the proxy in front of it
  cannot inject commands.
- Install: `taskq site agent install <machine>` (on the hub; the one step that still uses ssh, or runs here for the hub's own
  machine) puts `~/.local/share/taskq/agent.py` and the key there, adds one crontab line (every minute: start it unless it
  runs) and starts it. Then set `agent=True` for that machine in the machine table. The agent updates itself: when the
  hub's `agent.py` differs, it fetches it, checks signature and digest, runs its selftest and restarts on it while idle.
- Watch: `taskq site agent status` (last call, host, python, version); the health check reports `agent:<machine>` when an agent
  has not called for 30 minutes (`taskq site agent start <machine>` starts it over ssh when cron cannot). The agent's own log is
  `~/.local/state/taskq/agent-<machine>.log` on that machine.
- Clock: the agent also runs the machine's timed commands, so crontab holds only the agent's own line. `taskq site setup` writes
  them into `~/.config/taskq/agent-<machine>.clock.json`: on every pueue machine the boot step (`@reboot`: `on_boot.sh` or
  `taskq boot`, output to the boot log), on the hub also each `OUTPUTS["cron"]` entry calling `OUTPUTS["entry"]` (the health
  check). Times are crontab times in local time; `@reboot` runs once per boot (the boot id changed since the agent last ran).
  Minutes missed while the agent was down are made up for at most 10 minutes back, each command once; commands run detached and
  log their start and output to `~/.local/state/taskq/agent-<machine>.clock.log`. Stop the hub's clock with
  `echo '[]' | python3 ~/.local/share/taskq/agent.py clock <hub>`, start it again with `taskq site setup`.

### GPU pad

Inside a Slurm job, when the machine table has `gpu_pad=(floor, target, high)` (MiB), `queue/gpu_pad_start.sh` starts `queue/gpu_pad.py` in
the job: hold floor while nothing trains; grow to target once training memory is stable; yield when total usage exceeds high. The worker
grows it to floor before training (the `gpu_pad` consumer, or `taskq pad room`), and its memory is subtracted when computing free GPU memory.
The pad and the worker talk through files in this account's private dir on the node (`proto.gpu_pad_base`: `/tmp/taskq_gpu_pad_<uid>/<job>.mib`,
`.ready`, `.start`; the pad does not run when that dir is a link or another account's), read and written only as regular files of this
account, never through a link; a pad started by an older bundle is still found at `proto.GPU_PAD_BASE`.
Master switch: off while `R/queue/gpu_pad_DISABLED` exists in the executor root. Thresholds can also be given through `TASKQ_GPU_PAD_*`
env vars.

### Envs

Each machine's `envs` in the machine table says how to activate an env name: `('conda', name)`, `('venv', dir, base env)`, or `'spec'` /
`('spec', variant)` = built from a description.

#### Building envs

The description is `<config>/specs/<env>.yml` (`python`, `channels`, `conda`, `base`, `torch: {variant: {index_url, packages}}`, `pip`,
`pip_no_deps`), and the check is the same-named `.check.py`. With `AUTO["envs"]` on, each round looks at each machine's needed envs (those
written as `'spec'` in the machine table's `envs`, their base envs, plus those listed in `AUTO["envs"][machine]`): missing, description
changed, or build interrupted means queue a `taskq site env <machine> <env>` in the hub's core group (one at a time per machine); it
generates a bash snippet and runs it on that machine's CPU (Slurm uses `env_job`'s srun). A new version is built in `<name>-<hash>/` and
only after a passing check does the `<name>` symlink switch and `.ok` get written; running tasks are unaffected. Broken builds and lack of
space report `site:<machine>:env:<env>`. Executors whose env is not ready are not chosen when assigning tasks.

The hash (`mtab.spec_hash`, what `.ok` records) is the description plus the lock of the variant used there. Without a lock nothing pins the
rest, so the variant counts too (unless `default`), and a venv takes in its base's hashes: when the base is rebuilt the venv is rebuilt on
it. A lock pins its base's lock, so a venv with a current lock keeps its hash; a stale lock (`mtab.lock_stale`: the description changed
after locking, or the base was locked again) changes the hash and is not built from (lock it again), so an env never shows ready while
built from an old description or on an old base.

#### Env locks

`taskq env lock <name> [--variant V]` (or `--all`) resolves a description into `<name>.<variant>.lock.json`: exact versions, URLs and sha256
of every conda and pip package, with files downloaded into the hub state dir's `wheelhouse/`. With a lock, executors build offline: the hub
sends the locked files as blobs into that root, and the machine runs `conda create --offline` and `pip install --no-index --require-hashes`.
A pip package with no usable wheel is an error unless `--build-sdist` is given: building a wheel from its source package runs the
package's setup code on the hub. Only pure-Python (`none-any`) wheels built that way are kept (`wheelhouse/built/`), and later locks
use them without the flag.

### Smoke

With `AUTO["smoke"]` on, before a kind of task (recipe + params listed in `by` in the plugin's `smoke.py` + env) is first sent to an
executor, a small smoke task runs there (key `_smoke/<executor>/...`, nice -1000); only after it passes are real tasks sent. Definition:
`SMOKE = {recipe: dict(by=[param names], params=..., vars=...)}`; `params` and `vars` may be functions (real task params, store data dir)
computed on the store. Records live in the hub database's `smoke` table, one row per executor (passed, failed, queued); a real task of that kind finishing
there also counts as passed. `taskq smoke status`, `retry`, `adopt`.

### Other people's tasks (task files)

`taskq add --file <file.json>`: one `{field: value}` or a list. No `recipe` means `command`; `nice` is written in the file (several files
must agree); all other fields are recipe params (`command` needs `key`, `cmd`, `env`, `out`, `done`). Example:

```json
{"key": "alice/tune-01", "cmd": "python3 train.py --out {data}/alice/tune-01", "env": "torch",
 "out": "alice/tune-01", "done": "DONE", "resume": "ckpt_*.pt", "res": {"gpu_mem": 20000}, "owner": "alice", "nice": 5}
```

The command must be able to resume: after a release another worker continues on another machine from the checkpoint under `resume`, so
write checkpoints under `out`.

### Format cutovers

The on-disk format has a version, `proto.FORMAT`. Each place records the version its state is in, one line in a stamp file: the hub state
dir (`format`) and each executor and store root (`state/format`); no stamp is format 0. Code runs only on state in its own format: on
another, `taskq tick` does nothing but say (and push once) that `taskq self migrate` is needed, `taskq internal stage/fetch/archive`
refuse, and `taskq worker next` claims nothing (exit code 12, paused; tasks already running keep going); `taskq plan` notes it. Workers
of older bundles do not read the stamp. A new root made by relay and a new hub (no database yet) are stamped with the current format.

`taskq self migrate` holds one numbered step per format version (`migrate.STEPS`): step N takes a place from format N-1 to N and then
records N there, so each step runs once per place. By default (or `--list`) it only lists each place's format, the steps it needs and
what the hub's steps would change; it builds, pushes and writes nothing. `--apply` first reads every root and checks the hub steps
(anything wrong: nothing changes), holds the health check's round lock, copies the hub queue, database and stamp to
`<state dir>/snapshots/<time>-format<N>/` (the newest `proto.SNAPSHOT_KEEP` stay), migrates each root that is behind from the new
bundle (an executor switches to it with its unclaimed tasks set aside for a moment; claimed tasks keep running), then the hub. Run again,
it does nothing; a root that was unreachable is migrated on a later run. A step that changes only the hub's own storage (format 3: the
hub queue moves from `taskq/` into `taskq.db`) keeps every claim, copies the records one to one and compares the hub queue's status
before and after inside the same transaction; any difference rolls it back and stops.

A format change bumps `proto.FORMAT` and adds its step in the same commit; steps up to `migrate.MIN_FORMAT` are deleted once every place
is past them. The cutover: stop the hub's clock, push the code, (switch executors with `taskq site bundle`, or let migrate do it), `taskq self
migrate --apply`, start the clock (`taskq site setup`).

## File layout

Executor and store root R (the machine table's `root`, `proto.ROOT`):

| path | contents |
|---|---|
| `code/<bundle>/`, `code/current` | bundles; `current` points at the one in use |
| `queue/` | this machine's task queue (`ENABLED` is the master switch: without it queued workers exit at start) |
| `blobs/<first two>/<sha256>` | data files (may be symlinks to another disk) |
| `data/` | data dir: task views and outputs, `logs/tasks/` (part logs), `logs/seglogs.json` (what the health check last read from each part log; only new or changed logs are read again), `logs/workers/` |
| `state/` | `pins/`, `envs/` (env `.ok`), `hashes.db`, `view.lock`, `deploy.lock`, `format` (on-disk format stamp) |
| `tmp/` | half-transferred files |
| `envs/` | envs built on this machine |

Hub state dir (`proto.STATE_NAMES`): `taskq/` (the hub queue up to format 2; format 3 moves it into `taskq.db`), `relay/` (bundles and stage locks; `proto.RELAY_NAMES`), `health/`
(`proto.HEALTH_NAMES`), `taskq.db` (the hub queue, `queue/qstore.py`; events, problems, progress, results on the store; and the hub's bookkeeping, `queue/hubstate.py`:
what relay last read on each executor, the task records of pueue tasks the core added, relay's placement record per staged task and
each distinct set of staged input links once; the health check compacts it when mostly free pages), `format` (on-disk format stamp),
`snapshots/` (taken by `taskq self migrate --apply`), `wheelhouse/`, `tunnel*` etc.

Core source:

| dir | contents |
|---|---|
| `bin/taskq` | command line entry (`TREE`) |
| `queue/` | queue, worker, task specs, scheduling (advance, feed, relay, refill), site_ops, protocol `proto.py`, field tables `schema.py`, checks `check.py` |
| `queue/flow/` | experiment table -> instances and order |
| `queue/consumers/` | consumer plugins |
| `sites/` | machine table (`mtab.py`), executor types (`executors.py`; pueue / Slurm: `pueue.py`, `slurm.py`), ssh adapter helpers (`remote.py`), env builds (`envs.py`, `envlock.py`) |
| `sync/` | tunnel transfer |
| `monitor/` | health check, pushes, GPU usage records, state summaries |

## Command line and conventions

- The protocol lives only in `queue/proto.py`: on-disk names, time constants, task states, exit codes (table in [`../README.md`](../README.md)'s
  "Conventions"), field tables, alert formats, `TASKQ_*` env vars (`proto.ENV`). The rest of the core writes no such literals
  (`queue/test_protocol.py` checks).
- When a format changes (on-disk layout, queue, marker files, JSON fields, bundles), bump `proto.FORMAT` and put the rewrite of old state
  into `taskq self migrate` as that version's step; it runs once in the cutover. Code keeps no branch reading the old format.
- `--json` prints one JSON line, field tables in `proto.py`, with a `version`; frozen commands read back over ssh (`taskq status --json`,
  `taskq spec collect --json`) put that line behind `@@JSON `, and the hub reads only that line.
- `taskq worker`, `taskq spec` and `taskq internal` are for workers, programs on executors and the scheduler itself. Changes that go live
  without a cutover do not change `worker next/beat/release` arguments and exit codes, the versioned `status --json` and `spec collect --json`
  (fields add-only), or the launcher path inside a bundle (queued Slurm jobs find it at the same path under `code/current` when they start).
- Half-written files end in `.tmp` and are renamed when done; a half-built dir contains `.incomplete`.

## Adding things

- **New field**: add it to the table in `queue/schema.py` (`taskq check` verifies it automatically) and read it where used; then run
  `taskq machines fields --markdown` and paste the output between the matching markers here.
- **New command**: add it to `bin/taskq`'s `TREE` and `SECTIONS`, then add a row to the command table in `../README.md` (`queue/test_readme.py` checks).
- **New on-disk name, constant, exit code, env var**: add it only in `queue/proto.py`.
- **New executor difference**: write a consumer plugin (in the core's `queue/consumers/`, or the project's `consumers.py`); do not add a
  per-machine path in `consume.py`.
- **New scheduling method**: add an executor type (in the core's `sites/` registered in `executors.BUILTIN`, or the project's `executors.py`)
  implementing the interface in `sites/executors.py`; the core never branches on the `scheduler` value.
- **New result path**: count actual files on disk; write marker files last; while a transfer is running it is not done and the source is not
  cleaned up; add a "copied halfway" test.
- **Project-specific things** (model, dataset, machine name, path): put them in the project's config and plugins; when the core lacks an
  expression, add a general mechanism with tests (`queue/test_core_clean.py` checks).
