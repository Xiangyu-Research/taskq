# How taskq works

The overview, install, command table, tests and exit codes are in [`../README.md`](../README.md). This file covers config fields, how
each part runs, where files live, and how to add things.

## Structure

```
                         hub (role hub in machines.py)
   cron every 30 min ─→ taskq tick (monitor/health.py)
                        ├─ check every machine, push problems (monitor/plain.py, push.py), record them in the hub database (queue/db.py, events.py)
                        ├─ queue/advance.py   downstream steps: look at the store for finished work, add the next step to the hub queue
                        └─ queue/feed.py → queue/relay.py   send tasks, transfer data, top up workers, fetch, archive
                               │   refill.choose: pick an executor for each unclaimed task
                               │   relay_remote.op / store_op: run an operation of queue/site_ops.py on that machine
           hub queue (queue/taskq.py, under the hub's state dir)
                               │
        ┌──────────────────────┼─────────────────────────┐
   store (role store)      executor (pueue)              executor (Slurm)
   data dir = home of results  root R: code/ queue/      root R: same
   site_ops: probe, export,    blobs/ data/ state/       sites/slurm.py submits worker jobs
   pull, collect, archive      worker (consume.py)       a worker (consume.py) runs in the job
        │                      resident in a pueue group       │
        └── data moves directly between the store and executors (sync/tunnel.py, or a local copy on the same machine), never through the hub's disk ──┘
   backup machine (role backup): results to archive are backed up from the store (queue/archive_task.sh)
```

- The hub claims tasks from the hub queue on behalf of each executor (the queue records which executor got it), sends the inputs there
  and puts the task in that executor's own queue (`R/queue`, same key as the hub queue); the worker there claims, trains and releases;
  when the hub sees it finished, it fetches the results to the store. Executors do not talk to each other.
- One machine can hold several roles; the one with `ssh=None` is the hub's machine and can also be an executor (commands run locally,
  transfers copy locally).
- Executors run bundles built by the hub (`queue/relay_bundle.py`: the core files executors need go into `scripts/taskq/` inside the
  bundle, plus the project's config dir and the dirs listed in `OUTPUTS["bundle"]`); the bundle name is a content hash; it is pushed to
  `R/code/<bundle>` and `R/code/current` points at the one in use.

## Switches and config

The config dir holds two files: `machines.py` (machine table) and `policy.py` (how to use it). Fields, types and defaults are in
`queue/schema.py`; `taskq check` verifies against it (unknown fields are errors) and `taskq machines fields` prints it. The tables below
are generated by `taskq machines fields --markdown`, and `queue/test_readme.py` checks they match.

### Machine table

`MACHINES = {name: dict(...)}`, one entry per physical machine. Roles `roles`: `hub` (hub queue, health check), `store` (home of
results), `backup` (archive). An entry with `root` and `scheduler` is an executor:

- `scheduler="pueue"`: write `workers=[dict(...), ...]`, one resident worker per entry (fields in the next table). The core names workers
  in order: with a GPU it is `gpu<number>`, without it `cpu` (`cpu<number>` when several); the id is `<machine>-<name>` and the pueue group
  has the same name.
- `scheduler="slurm"`: write `jobs=dict(gpu=..., cpu=...)` (sbatch options); how many, QOS and time limits are in `policy.py`'s `SLURM`.

Pueue executors, the hub and the store all have the core's own pueue group `taskq` (`proto.IO_GROUP`: transfer, fetch, archive, env build,
unbounded concurrency). Manual groups are written in `manual_groups`; the core never queues into them (`taskq pueue-add` does). A `~` in
local paths such as `conda`, `root`, `data`, `repo` is expanded on this machine; a leading `~` in a remote command is left for the other
side to expand.

- `AUTO`: `advance` (queue the next step after training), `envs` (build envs automatically; may also be `{machine: [extra prebuilt envs...]}`),
  `revive` (restore pueued when it stops responding), `smoke` (smoke gate). A disabled part only records "what it would do" and changes nothing.
- `PAUSE`: paused machines are not contacted and get no tasks; they resume automatically at the deadline (hub local time), `None` means
  paused until the entry is removed. When the backup machine is paused, results that need archiving are released directly.
- `HOLD`: matching step instances are not queued (`advance` skips them).
- `PLACE`: keys are step names or training recipe names; values are allowed executors (order is preference) or `'any'`. Intersected with
  the spec's `machines`.

### Plugins

Plugins are found by filename in the plugins dir (`.taskq.toml`'s `plugins`); only these names are read per kind, and they import only
`taskq_api` (`queue/taskq_api.py`):

| file | exports | purpose |
|---|---|---|
| `recipes.py` | `RECIPES`, `HOOKS` | recipes; hook `model_of` (result dir -> the model param of the task that trained it) |
| `relay_plugins.py` | `PLUGINS`, `ACCEPTS`, `VIEW_ROOTS` | how to list inputs, build views and check results when sending to an executor (`queue/relay_plugins.py`, `sites/names.py`) |
| `consumers.py` | `CONSUMERS` | consumer plugins (see "Consumers") |
| `smoke.py` | `SMOKE` | smoke definitions (see "Smoke") |
| `labels.py` | `STEPS`, `QUIET`, `PLAN_TITLES` | plain words for pushes and progress reports (`monitor/plain.py`) |
| `readers/*.py` | `PROGRESS`, `INFO`, `TRAINED` | how to read progress, training settings and whether a round finished (`queue/spec.py` reads them, standard library only) |

Merging tables with duplicate keys is an error.

## Where to look when something is wrong

| want to know | look at |
|---|---|
| what is wrong now | `taskq problems` (found by the last health check; `--all` also lists notices and ones not yet due for a push) |
| what happened | `taskq events` (`--key`, `--site`, `--source`, `-f`); `relay`, `feed`, `advance` and `health` also write a plain text log (`OUTPUTS`'s `logs` dir, default home: `relay.log` etc.) |
| one task | `taskq show <key>` (spec and state), `taskq log <key>` (each part, events, hub task records), `taskq progress --key <key>` |
| what this round would do | `taskq plan` (read-only) |
| one executor | `taskq site status <machine>` (its queue), `taskq site envs <machine>` (envs); `relay/status.json` in the hub state dir |
| the worker itself | `data/logs/workers/` under the executor root (worker, GPU pad, Slurm job output); `pueue log` on a pueue executor |
| training output | part log `data/logs/tasks/<key>__<job>_part<part>.log` (on the executor; the fetch brings it to the same place in the store) |
| whether config is right | `taskq check` (`--quick` does not contact the store) |

Pushed problem ids are `<kind>:<machine or key>...` (kinds in `proto.ALERTS`); a problem is pushed once and disappears on its own when
fixed. "Things that happened" such as a reboot are acknowledged with `taskq notice ack`.

## How it runs

### Task queues

The hub queue and each executor queue are the same kind of queue (`queue/taskq.py`): `tasks.jsonl` has one task per line (nice `nice`,
arrival `order`, key, recipe, params), `claims/<key>/` is a claim (heartbeat every 5 minutes, stale after 20 minutes without one), and
there are records for failures, skips, missing inputs, releases and stops. Task states are in `proto.STATES`.

Claim order: lower nice first; within a nice, half-done tasks first (has a checkpoint, or this machine has part logs and no failure record);
then arrival order. The whole queue pauses claiming after 3 failures in 3 hours. A `taskq stop`ped task stops and is released by the
running worker within 30 seconds and is not claimed again; `taskq resume` undoes it. After the release the entry stays in the
executor's queue as `stopped` (its results kept) and does not disappear: check that a stop has finished by the "released" line in
`taskq events --source relay` or by the hub queue's state. Resumed before the release, the task continues on the same executor;
resumed after it, the next check deletes the executor's copy and its results and the hub queue dispatches it again with its current
params (a way to resend a not-yet-started task with changed params).

### Workers (consume.py) and consumers

A worker is `queue/consume.py` (`queue/worker_start.sh` activates the worker env, the second item of the machine table's `conda`,
and starts it; a name in `envs` is activated the same way as for tasks): it claims tasks from this
machine's queue, starts `queue/run_task.sh`, collects exit codes, sends heartbeats, stops and releases. `run_task.sh` activates the env
from the spec, sets env vars and runs the command at the project root inside the bundle, writing output to the part log; the training
command must resume from its checkpoint (after a release another worker continues from it).

#### Consumers

Differences between executor kinds live in consumer plugins: the core's `queue/consumers/` (in this order), then the project's
`consumers.py` `CONSUMERS`. A plugin is a module or dict; every hook (`consume.HOOKS`) is optional:

| hook | when |
|---|---|
| `active(w)` | start: whether this plugin applies (absent = yes) |
| `setup(w)` | start: set the worker's name, concurrency, time limit etc. |
| `admit(w)` | before claiming another task: returning a reason means do not claim yet |
| `before_start(w)` | before training starts |
| `env(w, env)` | before training starts: change env vars for `run_task.sh` |
| `tick(w)` | every round |
| `idle(w, why, now, since, err_since)` | nothing running: return seconds to sleep, `None` = exit |
| `on_exit(w)` | before exiting |

| plugin | what it does |
|---|---|
| `slurm` | in a Slurm job: job id as the worker name, concurrency from allocated CPUs and memory, job time limit, node-local staging dir, exit after an idle period |
| `resident` | resident worker in a pueue group: worker id as the name, cores and concurrency from the machine table's worker, exit after an idle period (exit 0, the hub starts it again next round) |
| `gpu_pad` | with a GPU pad: grow it to floor before training, subtract its memory when computing free GPU memory |
| `window` | the machine table worker's `hours`: do not claim outside the window; at the end of the window stop and release current tasks and exit |
| `gpu_idle` | claim only when no one else's processes are on the GPU and the usage records show no one else in the last `idle` minutes |
| `gpu_share` | a second task on one GPU: after the first has trained for a while, claim another when average utilisation is low and half the memory is still free |

How many tasks share a GPU and when to top up follow only this live state, never a model classification.

#### Workers in Slurm jobs

The hub tops up Slurm executors each round through `refill.slurm_plan` (`sites/slurm.py` submits `queue/worker.sbatch` or
`queue/cpu_worker.sbatch`): when the machine has tasks needing a GPU (ready and unclaimed, or training), fill every QOS quota in
`SLURM[machine]["gpu"]` so queued jobs keep accumulating queue time; pure CPU tasks are submitted up to the limit in `SLURM[machine]["cpu"]`.
The job's argument is `R/code/current/.../worker_start.sh`; `current` is resolved when the job starts, so it uses the bundle of that
moment; a worker switches to a new `current` only when claiming a new task.
When inputs must be copied to node-local disk (`res.local_inputs`), the copy runs in the background after training starts
(`queue/inputs.py`).

### Sending tasks: feed -> relay -> refill.choose

There is one entry point for sending tasks: the health check calls `run_all` in `queue/feed.py`, which hands off to `queue/relay.py`. Each round:

1. **Read** (`prepare`): one ssh per unpaused executor reads its queue, each task's progress, jobs, free space, envs and bundle
   (`site_ops status`, one `@@JSON` line); when its bundle differs from the hub's, push the new one first and read again. When space is
   below the first `budget` item, clean up (see "Data").
2. **Per-machine actions** (`plan`): for each task assigned to this machine in the hub queue --
   - not yet in its queue -> `stage` (queue `taskq internal stage` in the core group: the store sends missing data, builds the view, adds it
     to that queue; exit 75 = does not fit this round, transfer next time);
   - queued or training there -> `beat` (renew the hub queue claim); finished there -> `fetch` (fetch to the store and verify);
   - present on the store -> `drop` (remove the task and results there); if it needs archiving, `archive` first (store backs up to the
     backup machine; release only after success);
   - failed there: no progress -> `release --skip` (this machine will not claim it again); with progress -> keep the claim and report it;
   - stopped in the hub queue, stop undone, nice changed -> `rstop`, `rresume`, `rnice`; missing inputs there -> `restage`;
   - blocked by the bundle gate or smoke gate -> `hold`; unblocked -> `unhold`.
   - a failed `stage` / `fetch` / `restage` (mostly not the task's fault: tunnel down, busy disk timing out) is queued again at the next
     check, reported only after `XFER_TRIES` (`relay.py`) failures within one claim; stopped by hand is not retried; an old failed one
     queued again later is not reported by the health check.
3. **Assign** (`assign`, `refill.choose`): unclaimed tasks in the hub queue are assigned to machines in one pass. Order: nice -> half-done
   first -> arrival order. Each task's possible executors = intersection of `PLACE[step or recipe]` and the spec's `machines`, limited to
   machines with that worker kind (gpu / cpu); drop machines that skipped it (all skipped -> report `tqblocked`); a half-done task only goes
   to the machine with its progress; tasks whose inputs are already there come first. A machine must pass each of (`Site.fit`): has that
   worker kind, env ready, free slot (ready unclaimed below `READY[machine]`, negative nice does not count; when full it may swap out one
   without progress), inputs present on the store, fits (after inputs + `out_gb` at least the second `budget` item remains; with `blob_cap`
   the blobs disk is counted separately), plugin accepts, bundle gate and smoke gate do not block. Input sizes are measured on the store
   (`site_ops probe`).
4. **Do** (`finish`): carry it out, then top up workers: on a pueue machine start a worker when it is in its hours, none is alive, the
   previous one did not fail, and there is a ready unclaimed task of that kind there; on a Slurm machine submit jobs by the rules above.
   How many to start is computed only here; adapters in `sites/` only read state and follow instructions.

Alert when a machine is unreachable for more than 2 hours; send no tasks while all workers are outside their hours. Tasks assigned to a
name that is not an executor are reported by `feed.py`.

#### Bundle gate

Before sending a spec, run what the executor does with the spec on the hub using the bundle in use there (`queue/bundle_gate.py`); if it
fails, do not send (`hold`, report `bundlegate`) and check again after that machine switches bundles.

### After training: advance and flow

`queue/flow/compile.py` derives instances and order from the experiment table: within one task in order (training -> `after`'s first step
-> second ...); an input (wildcards included) that falls in another instance's outputs is ordered after that instance, across experiments;
inputs that fall in no output are raw data. Checks: unknown names in templates, wildcard outputs, overlapping outputs, an input inside its
own outputs, and cycles.

`queue/advance.py` each round:

1. checks on the store whether each instance is done (all `done` files present; still being fetched does not count);
2. adds to the hub queue any instance whose prerequisites are done, which is not done itself, and is not in the queue (recipe `command`,
   key = instance id, `step` = step name); which machine it goes to is decided by `PLACE` when sending;
3. steps with `rerun=True`: when an input is newer than the done file, delete the done file on the store and queue it again;
4. `temp`: after every instance using it is done and its results are on the store, delete those temp files on the store and record it in events.

`HOLD` matches are not queued; with `AUTO["advance"]` off it only writes "what it would queue".

### Store and site_ops

All operations that read or write data run on the machine holding the data: the hub runs `queue/site_ops.py <op>` inside that machine's
bundle through `relay_remote.op` (executor) or `store_op` (store) (arguments are JSON on stdin, the result one `@@JSON` line). The list of
operations is at the top of `site_ops.py`: for an executor root, `status`, `states`, `missing`, `pin`, `ingest`, `view`, `list`, `drop`,
`gc`, `env_mark`; for the store, `done`, `probe`, `rm`, `export`, `pull`, `collect`, `smoke`, `archive`; and `push` for sending files.

### Data: blobs, views, fetching

- **blob**: data files on an executor are stored by sha256 at `R/blobs/<first two>/<sha256>` (`proto.blob`); the adjacent `.st` records size
  and mtime when ingested, and a mismatch means drop and ingest again. The store's `export` lists the files and sha256 for a task (cached in
  `R/state/hashes.db`), and `push` sends only what is missing there; existing files on the same disk are hardlinked in (`ingest`).
- **views**: each task's inputs under `R/data` are built as symlinks to blobs following the store data dir's relative paths (`view`, never
  overwriting real files; a half-built dir contains `.incomplete`), and commands read paths under `{data}` as usual. A task being
  transferred or whose view is not ready pins its blobs (`R/state/pins/`).
- **cleanup** (`gc`, `queue/relay_store.py`): when free space is below the first `budget` item, delete views the hub queue no longer wants
  first, then blobs with no links by least recently used; pinned and half-transferred ones are left alone. `cap` and `blob_cap` limit the
  root and blobs.
- **fetch** (`fetch` -> the store's `pull`): that side lists outputs (`list`, same rule as "done") and fetches them to `.relay_in/<key>` under
  the store data dir, verifies them, moves them into place, and writes marker files (`MANIFEST.json`, top-level files) last. Done is judged
  by actual files on disk; while a copy, fetch or transfer is running it is not done and the source is not cleaned up.
- **archive**: tasks with `archive=True` are backed up from the store to the backup machine and verified by `queue/archive_task.sh` after
  the fetch.

#### Transfer

Bulk files between the store and executors go through `sync/tunnel.py`: the store runs a file service at the machine table's store
`transfer` address (a temporary address with `quick`), and all connections are initiated by the executor. The machine table's `tunnel`
says which direction this machine uses: `push` (store -> here, the other side downloads; on Slurm it may run on the `transfer_job` node),
`pull` (here -> store, chunked upload). Transfers on the same machine (such as a store that is also an executor, or an executor with
`ssh=None`) copy directly, hardlinking blobs, write to `.tunnelpart` and rename. `taskq tunnel rsync` is an rsync stand-in: transfer
through the tunnel first, then run rsync unchanged.

### GPU pad

Inside a Slurm job, when the machine table has `gpu_pad=(floor, target, high)` (MiB), `queue/gpu_pad_start.sh` starts `queue/gpu_pad.py` in
the job: hold floor while nothing trains; grow to target once training memory is stable; yield when total usage exceeds high. The worker
grows it to floor before training (the `gpu_pad` consumer, or `taskq pad room`), and its memory is subtracted when computing free GPU memory.
Master switch: off while `R/queue/gpu_pad_DISABLED` exists in the executor root. Thresholds can also be given through `TASKQ_GPU_PAD_*`
env vars.

### Envs

Each machine's `envs` in the machine table says how to activate an env name: `('conda', name)`, `('venv', dir, base env)`, or `'spec'` /
`('spec', variant)` = built from a description.

#### Building envs

The description is `<config>/specs/<env>.yml` (`python`, `channels`, `conda`, `base`, `torch: {variant: {index_url, packages}}`, `pip`,
`pip_no_deps`), and the check is the same-named `.check.py`. With `AUTO["envs"]` on, each round looks at each machine's needed envs (those
written as `'spec'` in the machine table's `envs`, their base envs, plus those listed in `AUTO["envs"][machine]`): missing, description
changed, or build interrupted means queue a `taskq site env <machine> <env>` in the hub's core group (one at a time per machine); it
generates a bash snippet and runs it on that machine's CPU (Slurm uses `env_job`'s srun). A new version is built in `<name>-<hash>/` and
only after a passing check does the `<name>` symlink switch and `.ok` get written; running tasks are unaffected. Broken builds and lack of
space report `site:<machine>:env:<env>`. Executors whose env is not ready are not chosen when assigning tasks.

#### Env locks

`taskq env lock <name> [--variant V]` (or `--all`) resolves a description into `<name>.<variant>.lock.json`: exact versions, URLs and sha256
of every conda and pip package, with files downloaded into the hub state dir's `wheelhouse/`. With a lock, executors build offline: the hub
sends the locked files as blobs into that root, and the machine runs `conda create --offline` and `pip install --no-index --require-hashes`.

### Smoke

With `AUTO["smoke"]` on, before a kind of task (recipe + params listed in `by` in the plugin's `smoke.py` + env) is first sent to an
executor, a small smoke task runs there (key `_smoke/<executor>/...`, nice -1000); only after it passes are real tasks sent. Definition:
`SMOKE = {recipe: dict(by=[param names], params=..., vars=...)}`; `params` and `vars` may be functions (real task params, store data dir)
computed on the store. Records live in the hub queue's `smoke/<executor>.json` (passed, failed, queued); a real task of that kind finishing
there also counts as passed. `taskq smoke status`, `retry`, `adopt`.

### Other people's tasks (task files)

`taskq add --file <file.json>`: one `{field: value}` or a list. No `recipe` means `command`; `nice` is written in the file (several files
must agree); all other fields are recipe params (`command` needs `key`, `cmd`, `env`, `out`, `done`). Example:

```json
{"key": "alice/tune-01", "cmd": "python3 train.py --out {data}/alice/tune-01", "env": "torch",
 "out": "alice/tune-01", "done": "DONE", "resume": "ckpt_*.pt", "res": {"gpu_mem": 20000}, "owner": "alice", "nice": 5}
```

The command must be able to resume: after a release another worker continues on another machine from the checkpoint under `resume`, so
write checkpoints under `out`.

### Format cutovers

When an on-disk format changes, run `taskq self migrate` once in a cutover (stop cron, hand back running tasks, push the code, switch every
executor to the new bundle) (lists by default, `--apply` changes; `--rename old=new`, `--merge old=old root`): the hub queue, relay
bookkeeping and smoke records on the hub, and queues and part logs in each executor and store root.

## File layout

Executor and store root R (the machine table's `root`, `proto.ROOT`):

| path | contents |
|---|---|
| `code/<bundle>/`, `code/current` | bundles; `current` points at the one in use |
| `queue/` | this machine's task queue (`ENABLED` is the master switch: without it queued workers exit at start) |
| `blobs/<first two>/<sha256>` | data files (may be symlinks to another disk) |
| `data/` | data dir: task views and outputs, `logs/tasks/` (part logs), `logs/workers/` |
| `state/` | `pins/`, `envs/` (env `.ok`), `hashes.db`, `view.lock`, `deploy.lock` |
| `tmp/` | half-transferred files |
| `envs/` | envs built on this machine |

Hub state dir (`proto.STATE_NAMES`): `taskq/` (hub queue), `relay/` (relay bookkeeping, `status.json`), `health/`, `taskq.db` (events,
problems, progress), `wheelhouse/`, `tunnel*` etc.

Core source:

| dir | contents |
|---|---|
| `bin/taskq` | command line entry (`TREE`) |
| `queue/` | queue, worker, task specs, scheduling (advance, feed, relay, refill), site_ops, protocol `proto.py`, field tables `schema.py`, checks `check.py` |
| `queue/flow/` | experiment table -> instances and order |
| `queue/consumers/` | consumer plugins |
| `sites/` | machine table (`mtab.py`), pueue / Slurm / ssh adapters (`pueue.py`, `slurm.py`, `remote.py`), env builds (`envs.py`, `envlock.py`) |
| `sync/` | tunnel transfer |
| `monitor/` | health check, pushes, GPU usage records, state summaries |

## Command line and conventions

- The protocol lives only in `queue/proto.py`: on-disk names, time constants, task states, exit codes (table in [`../README.md`](../README.md)'s
  "Conventions"), field tables, alert formats, `TASKQ_*` env vars (`proto.ENV`). The rest of the core writes no such literals
  (`queue/test_protocol.py` checks).
- When a format changes (on-disk layout, queue, marker files, JSON fields, bundles), put the rewrite of old state into `taskq self migrate`
  and do it in one cutover; code keeps no branch reading the old format.
- `--json` prints one JSON line, field tables in `proto.py`, with a `version`; frozen commands read back over ssh (`taskq status --json`,
  `taskq spec collect --json`) put that line behind `@@JSON `, and the hub reads only that line.
- `taskq worker`, `taskq spec` and `taskq internal` are for workers, programs on executors and the scheduler itself. Changes that go live
  without a cutover do not change `worker next/beat/release` arguments and exit codes, the versioned `status --json` and `spec collect --json`
  (fields add-only), or the launcher path inside a bundle (queued Slurm jobs find it at the same path under `code/current` when they start).
- Half-written files end in `.tmp` and are renamed when done; a half-built dir contains `.incomplete`.

## Adding things

- **New field**: add it to the table in `queue/schema.py` (`taskq check` verifies it automatically) and read it where used; then run
  `taskq machines fields --markdown` and paste the output between the matching markers here.
- **New command**: add it to `bin/taskq`'s `TREE` and `SECTIONS`, then add a row to the command table in `../README.md` (`queue/test_readme.py` checks).
- **New on-disk name, constant, exit code, env var**: add it only in `queue/proto.py`.
- **New executor difference**: write a consumer plugin (in the core's `queue/consumers/`, or the project's `consumers.py`); do not add a
  per-machine path in `consume.py`.
- **New scheduling method**: add an adapter in `sites/` (read state, submit jobs, start workers); how many to start is still computed in `relay.topup`.
- **New result path**: count actual files on disk; write marker files last; while a transfer is running it is not done and the source is not
  cleaned up; add a "copied halfway" test.
- **Project-specific things** (model, dataset, machine name, path): put them in the project's config and plugins; when the core lacks an
  expression, add a general mechanism with tests (`queue/test_core_clean.py` checks).
